## Resilient transcript ingestion

Normal cached ingestion is deliberately slow and sequential:

```powershell
python -m processors.cli ingest --kb table-tennis --request-delay 5 --jitter 2 VIDEO_URLS
```

Existing normalized files are reused without network access. Use `--force` only when a transcript must be refreshed. When YouTube blocks the transcript endpoint, the command stops the batch and writes the next permitted retry time to the gitignored `data/manifests/<kb>/ingest-retries.json` file. Do not immediately rerun a blocked batch.

Language selection is ordered and source-track based. The default comes from `language.transcript_priority` in the KB's `kb.yaml`; an explicit `--languages` list overrides it. The exact requested code is preferred, while a same-base regional code is used only when the exact track is missing—for example, `en` can fall back to manually created `en-US`. A language shown only under YouTube's translation languages is not considered an original subtitle track.

When ingestion discovers that a video is members-only, it records `classification: members_only` and `availability: members_only` in the same private retry manifest, marks the video as skipped, and schedules the next check three days later. The cp selector also excludes that video during the cooldown, so it does not repeatedly consume ingestion attempts.

The CLI enforces that cooldown before making another request. After changing to a genuinely different VPN or proxy route, pass `--retry-blocked` once to test the new route. Do not use the flag to retry the same blocked IP. Supplying `--proxy-url` or configured Webshare credentials also counts as an alternate route.

Prevention defaults are deliberately conservative: uncached videos are spaced by 20 seconds plus up to 20 seconds of random jitter, and one invocation stops after 10 successful uncached videos. Failed or cooling-down entries do not consume that success target, within a limited candidate window. Cached videos do not consume that budget. Do not defeat the cap by immediately launching repeated batches; leave a substantial break between runs. There is no universally safe request rate, especially on shared VPN or datacenter exits whose reputation is affected by other users. For sustained ingestion, use an operator-controlled rotating residential proxy and retain the same pacing.

## Account quota cutoff

Before each uncached LLM call, the shared budget guard reads actual Codex account rate limits through the read-only app-server `account/rateLimits/read` method. This is independent of local per-KB token counters and makes no model request. Configure `llm_budget.account_quota` in `config/processors.yaml`:

```yaml
account_quota:
  enabled: true
  stop_at_used_percent: 80
  five_hour_reset_grace_minutes: 10
```

At or above the cutoff, a 300-minute (five-hour) window blocks new calls only when **more than** the configured grace remains until its reset. Exactly 10 minutes remaining is exempt with the defaults. Window duration, not primary/secondary position, identifies the five-hour window. Weekly and other reported quota windows still block at the cutoff even near reset. The multi-bucket quota view takes precedence when available. Missing, malformed or expired quota information defers calls; it is never treated as zero usage. Local token budgets continue to apply, including during the grace period. Disabling the local token ledger does not disable an enabled account quota guard.

The guard uses the existing budget-deferred checkpoint path, so completed work survives and callers can resume after capacity recovers. It prevents the next LLM call, does not kill an in-flight call, and cannot prevent other account activity from changing quota between checks. Existing long-running campaigns must restart/resume to load this code/configuration. No automatic quota reset or credit purchase is performed.

Official protocol: https://learn.chatgpt.com/docs/app-server#6-rate-limits-chatgpt
